## Commands

This project uses **bun** as the package manager and runtime (`packageManager: bun@1.3.11`).

- `bun install` — install dependencies
- `bun --bun next dev` (or `bun dev`) — start the dev server
- `bun --bun next build` (or `bun run build`) — production build
- `bun --bun next start` (or `bun start`) — run the production build
- `bun run lint` — run ESLint (flat config via `eslint.config.mjs`)

There is no test suite configured in this repo yet.

## Critical: this is not the Next.js you know

`package.json` pins `next@16.3.0`, a version newer than most training data and with breaking API/convention changes from earlier Next.js releases. Per [AGENTS.md](AGENTS.md), **read the relevant guide under `node_modules/next/dist/docs/` before writing App Router code** (routing, layouts, data fetching, config, etc.) rather than relying on prior knowledge of Next.js. Key subfolders: `01-app/01-getting-started`, `01-app/02-guides`, `01-app/03-api-reference`.

One concrete example already in use: route/layout prop types are generated and consumed as `LayoutProps<"/">` / `PageProps<"/...">` (see [app/layout.tsx](app/layout.tsx)) instead of hand-written `{ children }: { children: React.ReactNode }` props — check the docs/generated `.next/types` before assuming a prop shape.

The Next-version warning block in AGENTS.md is regenerated by `next dev` (`node_modules/next/dist/server/lib/generate-agent-files.js`) — don't strip it out.

## Architecture

- **App Router** (`app/`): currently a single route — `app/layout.tsx` (root layout, fonts, metadata) and `app/page.tsx` (home page, composed from section components). `app/test/` holds a scratch/example route.
- **Sections vs. primitives**: page content is built by composing page-specific section components from `components/sections/` (`hero.tsx`, `features.tsx`, `community-benefits.tsx`, `trending-destinations.tsx`, `cta-banner.tsx`) plus shared chrome components `components/navbar.tsx` and `components/footer.tsx`. Generic, reusable UI primitives (button, dialog, sidebar, etc.) live in `components/ui/` and are shadcn/ui-generated — treat them as vendored; prefer composing/extending over hand-editing internals unless fixing a real bug.
- **Path alias**: `@/*` maps to the repo root (`tsconfig.json`), e.g. `@/components/...`, `@/lib/utils`, `@/hooks/...`.
- **shadcn/ui config** (`components.json`): style `radix-vega`, base color `mist`, icon library `lucide`, CSS variables on, no Tailwind prefix. Aliases: `components` → `@/components`, `ui` → `@/components/ui`, `lib` → `@/lib`, `hooks` → `@/hooks`, `utils` → `@/lib/utils`. Adding new shadcn components should go through the `shadcn` CLI (in devDependencies) so it respects this config rather than being hand-created.
- **Styling**: Tailwind CSS v4 (`@tailwindcss/postcss`, no `tailwind.config.*` — config lives in `app/globals.css`). The `cn()` helper in `lib/utils.ts` merges class names via `clsx` + `tailwind-merge`; use it instead of manual string concatenation for conditional classes.
- **Fonts**: loaded via `next/font/google` in `app/layout.tsx` (Geist, Geist Mono, DM Sans) and exposed as CSS variables consumed by Tailwind.
